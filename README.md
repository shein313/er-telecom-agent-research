Исследование и выбор оптимальной архитектуры AI-агента первой линии поддержки (L1)

Проект выполнен в рамках дисциплины «Проектная деятельность» (СПбГУТ, 3 курс, ИТПИ).
Тематика: Исследование и поиск оптимальной архитектуры для AI-агента поддержки первой линии (чаты)(«ЭР-Телеком»).

1. Цель и постановка задачи

Цель работы — сравнить четыре варианта построения AI-агента для чатов первой линии поддержки и выбрать оптимальную архитектуру по балансу трёх показателей:
- Качество ответа (оценка от 1 до 5 баллов): насколько точно агент следует регламентам, не выдумывает ли лишнего и вовремя ли переводит сложные случаи на оператора.
- Задержка (latency): медианное время ответа (P50) и время, быстрее которого обрабатываются 95% обращений (P95).
- Стоимость: средние затраты на обработку одного обращения и 1 000 обращений с учётом расхода токенов.

2. Сравниваемые архитектуры

- A_Simple_LLM (базовый вариант): прямой запрос клиента в языковую модель с системным промптом без доступа к базе знаний.
- B_LLM_RAG: поиск подходящих регламентов в базе знаний (TF-IDF + косинусное сходство, top_k=2) и передача найденного текста в модель.
- C_Router_RAG (маршрутизация): предварительная классификация обращения по категориям (технические сбои, оплата и тарифы, эскалация, запросы не по теме), быстрые шаблонные ответы для аварий/расторжения договора и поиск только по нужному разделу базы знаний.
- D_Tool_Agent (агент с инструментами): автономный цикл обработки, в котором модель сама решает, когда вызывать поиск по базе знаний или оформлять заявку на выезд мастера/перевод на оператора.

3. Методика эксперимента

- Модель: openai/gpt-4o-mini (temperature=0.1 для ответов, 0.0 для классификации и оценки).
- База знаний (data/knowledge_base.json): 8 регламентов провайдера (индикация LOS на оптическом терминале, настройка Wi-Fi 2.4 и 5 ГГц, сроки зачисления СБП, услуга «Обещанный платеж», тарифы, правила перевода аварийных обращений).
- Тестовая выборка (data/test_dataset.json): 30 обращений клиентов по 6 категориям, включая неполные запросы и провокации не по теме.
- Оценка качества: автоматизированная проверка ответов (LLMJudge) по эталонным критериям для каждого кейса от 1 до 5 баллов.

5. Выводы и рекомендация

Оптимальной архитектурой для первой линии поддержки оказалась C_Router_RAG (средний балл 4.47 из 5 при стоимости $0.099 за 1 000 обращений):
- На аварийных обращениях, вопросах расторжения договора и запросах не по теме маршрутизатор срабатывает за 0.49–0.68 секунды без вызова генерации ответа, что снижает расходы и полностью исключает риск выдуманных ответов.
- Фильтрация документов по категории (отдельно биллинг, отдельно техподдержка) убрала путаницу в поиске, из-за которой обычный RAG ошибался в вопросах списаний и тарифов.

Почему остальные варианты подходят хуже:
- A_Simple_LLM работает быстрее и дешевле всех, но без базы знаний не знает тарифов и регламентов (оценка 3.10).
- B_LLM_RAG даёт хорошее качество (4.13), но тратит больше токенов и чаще ошибается при пересечении терминов в документах.
- D_Tool_Agent обходится в 3.1 раза дороже базового варианта ($0.182 за 1 000 обращений) и дольше отвечает из-за нескольких последовательных вызовов модели, при этом нестабильно ведёт себя на неполных запросах.

Рекомендация: для внедрения в поддержку первой линии стоит использовать связку Router + Filtered RAG, а для дальнейшего развития добавить в маршрутизатор отдельную ветку уточняющих вопросов для неполных обращений.

6. Запуск стенда

1. Создать и активировать виртуальное окружение:
python -m venv .venv
.\.venv\Scripts\activate

2. Установить зависимости:
pip install -r requirements.txt

3. Указать ключ API в файле .env:
OPENROUTER_API_KEY=ваш_ключ

4. Запустить эксперимент и построение графиков:
python -m evaluation.runner
python -m evaluation.plot_results
